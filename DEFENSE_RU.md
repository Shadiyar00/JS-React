# Как работает StudyShelf

## Запуск на Windows

Распакуй проект. Открой папку в VS Code, затем Terminal → New Terminal. Выполни `npm install`, затем `npm run dev`. Открой адрес из терминала. Для остановки нажми Ctrl+C. Нужен установленный Node.js.

## Главная идея

Это SPA — приложение с одним HTML-документом. React меняет отображаемые компоненты при переходах. В адресе используются #/ (каталог), #/add (форма), #/resource/id (подробности). Сервер не должен создавать отдельную HTML-страницу для каждого ресурса.

Данные — массив объектов из JSON. Каждый объект содержит id, title, topic, level, format, minutes, description, url и createdAt. Есть 120 учебных задач; ссылка ведёт на документацию по соответствующей технологии. При первом запросе API копирует массив в localStorage. Новые записи сохраняются там же. Это разрешённая заданием имитация API, поэтому сервера и общей базы пользователей нет.

## Путь данных

Catalog вызывает resourcesApi.list(query). API ждёт 350 мс, читает localStorage и вызывает queryResources. Сначала данные фильтруются, затем сортируются, затем выбирается нужная страница. Promise возвращает результат. setResult сохраняет его в state, React повторно вызывает компонент и показывает карточки через map.

ResourceCard получает объект через props item. Props — входные данные от родительского компонента. Карточка не меняет объект. FilterBar получает query и функцию onChange. Когда пользователь печатает, обработчик передаёт новое значение обратно в Catalog. Это поток данных вниз через props и событий вверх через функции.

## Где находится state

App хранит только текущий маршрут. Catalog хранит запрос, результат, состояние загрузки, ошибку и повторный запрос. ResourceDetail хранит одну запись. ResourceForm хранит введённые значения и ошибки. Так каждый компонент отвечает за свою часть интерфейса.

useState возвращает текущее значение и функцию его обновления. В `setQuery(previous => ({...previous, page: 1}))` мы создаём новый объект, сохраняя остальные поля. Нельзя менять предыдущий объект напрямую.

## Управляемая форма

`value={values.title}` задаёт значение из state. `onChange={change}` обновляет state при вводе. Поэтому React знает актуальное значение поля. submit вызывает preventDefault, чтобы браузер не перезагружал документ, проверяет поля и вызывает API. Кнопка блокируется во время сохранения. После успеха показывается ссылка на созданную запись.

## useEffect и очистка

Эффект Catalog зависит от [query, retry, fail]. Меняется поиск, фильтр, сортировка или страница — меняется query и запускается запрос. retry — счётчик для повторного запроса. fail управляет тестовой ошибкой.

Эффект возвращает `() => controller.abort()`. Перед следующим запуском или при удалении компонента React выполняет очистку. Старый таймер отменяется, а проверка signal.aborted запрещает сохранять устаревший ответ. Это защита от race condition: медленный старый ответ не должен заменить новый.

В App effect с [] подписывается на hashchange и при очистке удаляет тот же обработчик. В StrictMode при разработке React дополнительно проверяет цикл setup → cleanup → setup, поэтому очистка особенно важна.

## Темы для защиты

- Re-render: React снова вызывает компонент после обновления state, изменения props от родителя или изменения context. Это ещё не означает изменение всех DOM-узлов.
- Render: вычисление того, какой должен быть интерфейс. Commit: применение необходимых изменений к DOM. Эффект выполняется после commit; не следует объяснять его как код, который вызывается перед render.
- State snapshot: обработчик видит значения из того render, в котором он создан. setState не меняет текущую переменную немедленно.
- Batching: React может объединить несколько обновлений состояния в один render. Для обновления на основе предыдущего значения используем функцию: `setRetry(value => value + 1)`.
- Stale closure: функция продолжает использовать старое значение из своего замыкания. Правильные зависимости эффекта и функциональные обновления помогают избежать ошибки. Отмена запроса решает отдельную проблему устаревших асинхронных ответов.
- Reconciliation: React сравнивает новое дерево с предыдущим и определяет изменения.
- Key: стабильный id помогает сопоставить элементы списка. Индекс ненадёжен при добавлении или перестановке. UUID создаётся при сохранении записи, а не при каждом render.
- Component identity: тип, позиция и key определяют сохранение state. FilterBar не определяется внутри Catalog. У ResourceDetail key равен id: при переходе к другой записи его state сбрасывается.
- State preservation: обычный re-render сохраняет state. Удаление компонента из дерева сбрасывает его. Поэтому уход с каталога на другую страницу и возвращение сбрасывает фильтры. Сам каталог данных сохраняется в localStorage.

## Что изменить на защите

Дополнительный фильтр: добавь поле в defaults, controlled input в FilterBar и соответствующее условие в queryResources. Страница должна сбрасываться на 1.

Дополнительная сортировка: добавь option в Catalog и ветку компаратора в queryResources.

Новое поле карточки: проверь наличие поля в JSON и выведи `item.поле` в ResourceCard.

Размер страницы: передай pageSize в query или измени значение по умолчанию в queryResources.

Сброс формы: `setValues(initial)` заменяет все введённые значения исходными.

## Короткая речь на английском

My project is StudyShelf, a catalog of IT learning resources. It is a React single page application. I use a simulated asynchronous API and localStorage. The initial catalog has 120 records. Users can search, filter, sort, open details, and add a resource. Each page has its own state. I pass data through props. My effects cancel old requests to prevent stale results. The application handles loading, errors, empty results, and successful saves.
